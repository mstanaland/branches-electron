# The background fetch is always on and focus-gated

Nothing on the local filesystem changes when a branch is merged upstream, so ahead/behind counts were only ever as fresh as the user's last manual fetch. Main now runs `git fetch --prune` for the active repository every two minutes, chaining each tick after the previous one finishes rather than firing on a fixed timer, and only while the window has focus — a backgrounded app makes no network calls. A repository with no remote schedules nothing. Failures are quiet: no banner, no modal, and repeated failures back off to a cap of 8× the interval, because an offline laptop or a remote that refuses credentials should go silent rather than retry every tick. Every git call sets `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=echo` and `SSH_ASKPASS_REQUIRE=never`, so a credential prompt is a fast error instead of a child process waiting on a terminal that isn't there; `GIT_SSH_COMMAND` is deliberately left alone, since setting it would override a repository's `core.sshCommand`.

We considered making it opt-in per repository, or adding a preference to disable it, and shipped it always-on with no setting: two minutes of one fetch while you are looking at the window is not load worth a preference. A setting can come later if it proves annoying.

Consequence: the renderer must tell main which repository is active (`setActiveRepository`), and main pushes `onRemoteRefsChanged` back when a fetch moves a ref, which the renderer answers by re-reading branches and status. The fetch goes through the per-repository write queue, so a user's write can wait behind a fetch in flight — the alternative was a background tick taking a ref lock that a checkout the user just asked for needs.
